## ⚠ Risks carried by this suite

- **`W1` · The whole money path is NOT in this suite.** 21 engine cases *(conversion · quarantine · per-run snapshot · rounding exactly once · expected arrival date)* **left the suite on 23/09** by the owner's decision: they depend on the `US006` engine, and `US006` belongs to a **future sprint**. They are verified in `US006`'s own suite, not here. ⚠️ **The consequence has to be said out loud:** this suite passing 100% still proves **nothing** about a single amount being correct — it proves the **configuration register** is right, not **how money is computed from that register**. Anyone reading US080's pass rate as a statement about money is reading it wrong. The trace of those 21 rules stays in `CM_US080_EN_v1.md` as `Skipped` rows with a stated reason. For the same "future sprint" reason, `BR-14.V1` *(this register is **not** used for the `FX-05` shipping-fee ladder)* left with `US009` — **22 rules** in total moved to another US's suite.
- **`W9` · 8 cases re-blocked 24/09 — missing evidence, not a missing decision.** `TC_US080_037` · `_052` · `_070`–`_075` were unblocked on 23/09, then **re-blocked** on 24/09 after a review found: the earlier `Ready` state carried no evidence at all — no signed API contract, no deployed endpoint, no successful test call — it rested only on the pre-condition having been written as a sentence. **Marking a case `Ready` with no evidence is an unsupported readiness claim.** All 8 cases are `BLOCKED`, `Owner: Dev`, lifted once the contract and endpoint are usable with concrete evidence, not merely once a decision is made to unblock them. 🆕 **25/09: 5 of the 8 lifted with evidence** (`_037` · `_052` · `_070` · `_071` · `_075` — deployed endpoint + successful test calls, see their `Remark`). 3 stay `BLOCKED`: `_073`/`_074` (feature not built, Owner KE) and `_072` (endpoint deployed, but a real `DELETE` on the shared environment is not acceptable).
- **`W2` · The SRS is 🟡 Draft and has not been through KE** — and the risk has already materialised once: KE review on 18/09 → **six bumps in three days** (`v1.9`→`v1.14`), reversing the business direction. Keep budget for at least one `update-test-cases` pass.
- **`W3` · `OQ-KO-02` is still open** — there is no **official** term for `ALREADY_KRW`; most Korean strings are BA-proposed and not KE-confirmed. KE's answer could change expected results in bulk.
- **`W4` · 5 error codes + the `SETTLEMENT_CONFIG` permission code + the table name are all `[proposed]`**, not yet minted (`OQ-121`, owned by **KE** — `US076` only compiles the request and cannot mint). Every case therefore **asserts the message text**, with the code recorded in `Remark` behind a `[proposed]` label — if Dev renames a code, only `Remark` changes, not the steps.
- **`W5` · Responsive scope conflict** — the Blueprint names viewports `1920/1366/768/390`; the Test Strategy puts mobile · tablet · anything below `1366×768` **out of scope**. This suite follows the **Test Strategy** (`R-ENV`); `768`/`390` are reported as a scope conflict rather than written as cases that cannot run.
- **`W6` · The prototype has no server** — the three branches of `comp 36` (`409 PMP-1002` · `409 PMP-1001` · `5xx`) have no capture; `PMP-1003` has **no UI path** by design.
- **`W7` · 10 cases act on `US120`'s screen**, not US080's (`LIFECYCLE_CONTRACT #406`). **They were unblocked on 23/09** and now count as runnable — but their pre-conditions still **name the 변경 승인 screen explicitly** and still require **two accounts of different identity** (`BR-7.V6`). Whoever schedules them must be able to produce both; missing either, these 10 cannot run even though their status reads `Ready`.
- **`W8` · `SRS_US120` still specifies the queue by ROLE NAME (`APPROVER`)** — the mechanism `US069` `BR-9` measured the platform does not implement. The approver account may not be creatable that way — a gap for BA-4.

## Scope notes

- **UI language: the system is Korean only.** Every control, label and message is written **`KO (EN)`** — the Korean string in bold, followed by an **English gloss** in brackets (`R-LANG`). The gloss is a **copy of the `en:` column of `UIMapping/US080_UIMapping.md`**, not a translation made here.
- **Pre-conditions follow the same `KO (EN)` convention**, and **name the screen** when the state is built on another US's screen — 10 cases use `US120`'s **변경 승인** (Change Approval) screen. Every pre-condition line must be a **state that can be built**: an account/session · a record in a named state · an environment capability *(an endpoint that can be called, query logging switched on)*. No line may be *"read document X"* or *"know X"* — that belongs in `Remark`.
- **Categories come from the CLOSED list of 12 labels** (`testcase-rules.md` §3). The `[API]` block now holds **7 cases, all of them genuine HTTP calls** (`TC_US080_070`–`_076`) — the 22 engine cases that used to stretch this label have left the suite, so the trade-off recorded in the Coverage Matrix's `Category decision` block **no longer applies**; that block is kept as a historical record.
- **`[API]` is a CATEGORY; "needs an API contract" is a DEPENDENCY — two different sets, do not conflate them (review 24/09, `Finding 5`).** A category does not change just because a case calls an API to set up or execute — it reflects what the case verifies (a UI behaviour, a business rule, an HTTP call), not the tool used to build it.

  | | Cases | Why |
  |---|---|---|
  | **Category `[API]`** *(7 cases)* | `TC_US080_070`–`_076` | The case verifies an HTTP call — exactly what the label means |
  | **Depends on an API contract/endpoint** *(8 cases — 5 `Ready` since 25/09, 3 `BLOCKED`: `_072` · `_073` · `_074`)* | `TC_US080_037` · `_052` · `_070`–`_075` | Can only be staged by calling the API directly — independent of category |
  | Overlap | `_070`–`_075` (6 cases) | Both `[API]` category and dependent |
  | Category only, not dependent | `_076` | `[API]`, but **Ready** — it was blocked earlier by a missing consumer (`US074`/`US075`), not by Dev's missing contract |
  | Dependent only, not category | `_037` (`[Create]`) · `_052` (`[Detail]`) | UI/Detail cases that must call the API directly to stage the state they check |
- **`PMP-*` error codes are `[proposed]`** ⇒ assert the **message text**, never the code. The code lives in the `Remark` column.
- **Two UI Mapping strings are deliberately touched by no case:** **대기 중인 요청이 없습니다** (Nothing is waiting for approval) is the empty state of `US120`'s queue — it belongs to that US's suite, not to this register; **영향받는 건수** (Impact count) is **structurally always 0** for this register (`BR-8` snapshots at run start), so there is no value to verify.
- **Out of scope:** the behaviour of the `US006` engine *(only the data contract this register supplies is checked)* · KE's `결제수단 관리` screen · the `FX-05` ladder of `US009`.
